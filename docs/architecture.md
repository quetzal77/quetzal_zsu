# Архітектура порталу з'єднань ЗСУ

Проєктний документ · чернетка v2

- **Тип проєкту:** довідковий портал про з'єднання (бригади, полки, батальйони тощо), битви та
  традиції ЗСУ, низьке навантаження. Термін «з'єднання», а не «бригада» — портал охоплює й інші
  типи з'єднань, і загальну структуру ЗСУ, яку одними бригадами не описати; таблиці в БД
  (`brigades`, `brigade_battles` тощо) лишили історичну назву.
- **Дані:** SQLite (`quetzal_zsu.db`), схема — `schema.sql`
- **Бюджет:** $0 / місяць

План для сайту на базі `quetzal_zsu.db` — від переліку функцій до розгортання на безкоштовному хостингу.

## 1. Затверджений функціонал

| # | Функція | Рішення |
|---|---|---|
| 1 | Перегляд і навігація | Список з'єднань з фільтрами за родом військ (`military_branches`), корпусом (`army_corps`), територіальним командуванням (`territorial_commands`), типом з'єднання (`unit_types`) та регіоном (`regions`/`locations`); детальна сторінка з'єднання з битвами, спорядженням і традиціями |
| 2 | Редагування | Так, через форму на фронтенді, захищено логіном (див. розділ "Авторизація" в `CLAUDE.md`) |
| 3 | Фото | До 3 фото на з'єднання (емблема + додаткові), поле опціональне — з'єднання може бути й без жодного фото |
| 4 | Хронологія битв | Сторінка битви (`battles`) з датами, локацією та переліком з'єднань-учасників і їх ролі (`brigade_battles.role`) |
| 5 | Каталог спорядження і традицій | Перегляд `equipment` і `traditions` як довідників, з переліком з'єднань, за якими закріплена кожна позиція |
| 6 | Статистика по з'єднанню | Похідні лічильники на сторінці з'єднання — кількість битв, одиниць спорядження, традицій (агрегація по `brigade_battles` / `brigade_equipment` / `brigade_traditions`, без окремих таблиць) |
| 7 | Структура ЗСУ | Сторінка `/zsu` — види ЗСУ, роди військ і сил, спецслужби; окремі роди розкриваються по мірі наповнення даними |
| 8 | Аудиторія | Відкритий довідковий сайт — усі охочі, орієнтир ~сотні відвідувачів |
| 9 | Мова | Тільки українська |

**Припущення, яке закладаю в архітектуру:** перегляд сайту не обмежується логіном, а редагування
даних про з'єднання, битви, спорядження, традиції й довідники — обмежене (`require_login`), щоб
випадкові відвідувачі не могли зіпсувати дані. Нові облікові записи редакторів створюються вручну
(`create_user.py`), без публічної форми реєстрації.

## 2. Структура проєкту

Базова розкладка файлів для FastAPI-застосунку, що читає `quetzal_zsu.db` напряму.

> Це знімок первинного планування (чернетка v2); фактична структура вже відрізняється й
> розвивається — канонічний опис поточних роутерів і шаблонів веди в [`CLAUDE.md`](../CLAUDE.md).

```
brigade-portal/
├── app/
│   ├── main.py                # точка входу FastAPI, реєстрація роутів
│   ├── database.py            # підключення до SQLite, сесії
│   ├── models.py               # Pydantic-схеми (Brigade, Battle, Equipment, Tradition, Location...)
│   ├── routers/
│   │   ├── brigades.py        # /brigades, /brigades/{id}, форма створення/редагування
│   │   ├── battles.py         # /battles, /battles/{id}
│   │   ├── equipment.py       # /equipment
│   │   ├── traditions.py      # /traditions
│   │   └── locations.py       # /locations, /regions — довідники географії
│   └── templates/              # Jinja2 HTML-шаблони
│       ├── base.html
│       ├── index.html         # реєстр з'єднань з фільтрами
│       ├── brigade_detail.html # битви, спорядження, традиції, фото
│       ├── brigade_form.html  # створення/редагування з'єднання + фото
│       ├── battle_detail.html # дата, локація, з'єднання-учасники
│       ├── equipment_list.html
│       └── traditions_list.html
├── static/
│   ├── css/
│   └── img/                    # емблеми та фото з'єднань (до 3 на з'єднання)
├── data/
│   └── quetzal_zsu.db          # на проді — на persistent volume
├── schema.sql                  # канонічна версійована схема БД
├── requirements.txt
├── Dockerfile
└── fly.toml                    # конфіг хостингу (розділ 4)
```

### Нова таблиця в `quetzal_zsu.db`

Функціонал з розділу 1 (пункт 3, "до 3 фото на з'єднання") вимагає одного розширення поточної схеми — решта функціоналу (фільтри, битви, спорядження, традиції, статистика) вже покривається наявними таблицями `brigades`, `battles`, `army_corps`, `military_branches`, `territorial_commands`, `troop_types`, `unit_types`, `locations`, `regions`, `equipment`, `traditions` та junction-таблицями `brigade_battles`, `brigade_equipment`, `brigade_traditions` (див. `schema.sql`):

| Таблиця | Призначення | Ключові поля |
|---|---|---|
| `brigade_photos` | до 3 фото на з'єднання, поле опціональне | `photo_id`, `brigade_id → brigades`, `file_path`, `position` (1–3) |

Існуюче поле `brigades.emblem_file` залишається як є (основна емблема); `brigade_photos` — для додаткових фото, які раніше в схемі не передбачались. Таблиці й колонки лишили історичну назву `brigade*` — перейменування на «з'єднання» торкнулось лише текстів інтерфейсу.

Статистика по з'єднанню (кількість битв/спорядження/традицій) — окремої таблиці не потребує, рахується запитом-агрегацією по `brigade_battles`, `brigade_equipment`, `brigade_traditions`.

### Сервіси всередині застосунку

| Сервіс | Роль |
|---|---|
| **Uvicorn** | ASGI-сервер, що запускає FastAPI-застосунок у продакшені |
| **FastAPI** | маршрутизація, обробка запитів, валідація вхідних даних |
| **Jinja2** | рендеринг HTML-сторінок із даних про з'єднання й битви |
| **sqlite3 (stdlib)** | прямі запити до `quetzal_zsu.db` без ORM |
| **StaticFiles** | віддача CSS та зображень із `/static` |
| **python-multipart** | приймання форм і файлів фото з'єднань |

## 3. Технології та архітектурна схема

### Стек

| Шар | Технологія | Навіщо |
|---|---|---|
| Мова | Python 3.12 | основна мова бекенду |
| Веб-фреймворк | FastAPI | маршрути, валідація, автодокументація API |
| Сервер застосунку | Uvicorn | виконує FastAPI як ASGI-процес |
| Шаблони | Jinja2 | генерація HTML-сторінок на сервері |
| База даних | SQLite (`quetzal_zsu.db`) | вже готова схема (`schema.sql`), без окремого сервера БД |
| Стилі | звичайний CSS (без збірки) | простота — не потрібен build-крок для довідкового сайту |
| Контейнеризація | Docker | однаковий запуск локально й на хостингу |
| Хостинг | Fly.io (див. розділ 4) | безкоштовний persistent volume для файлу БД |
| Версіонування | Git + GitHub | історія змін, джерело для деплою |

### Схема архітектури

```
                     ┌─────────────────────────────┐
                     │      Браузер відвідувача     │
                     │   телефон / ноутбук — HTML+CSS │
                     └───────────────┬─────────────┘
                                      │
                             HTTPS · GET /brigades/{id}
                                      │
                                      ▼
        ┌───────────────────────────────────────────────────┐
        │             Fly.io — контейнер (Docker)            │
        │  ┌───────────────┐        ┌───────────────────┐   │
        │  │   Uvicorn     │        │  FastAPI + Jinja2  │   │
        │  │ (ASGI-сервер) │───────▶│ роути, рендеринг    │   │
        │  └───────────────┘        └─────────┬──────────┘   │
        │                                      │              │
        │                          SQL-запити (sqlite3)       │
        │                                      ▼              │
        │                        ┌──────────────────────┐     │
        │                        │   quetzal_zsu.db      │     │
        │                        │ persistent volume —  │     │
        │                        │ не зникає при        │     │
        │                        │ передеплої           │     │
        │                        └──────────────────────┘     │
        └───────────────────────────────┬───────────────────┘
                                         ▲
                              git push → build → deploy
                                         │
                         ┌───────────────────────────────┐
                         │      GitHub-репозиторій       │
                         │ джерело коду, тригер деплою   │
                         │           на Fly.io           │
                         └───────────────────────────────┘
```

## 4. Де розмістити портал

Тільки безкоштовні варіанти. Головний критерій відбору — чи диск, на якому лежить `quetzal_zsu.db`, зберігається між перезапусками контейнера.

### Fly.io — рекомендовано

| | |
|---|---|
| Персистентність диска | Так — окремий volume, файл БД зберігається назавжди |
| Що потрібно | Fly CLI, Dockerfile, акаунт (потрібна прив'язка картки для верифікації, списань немає в межах free allowance) |
| Ліміти free tier | ~3 малі VM, 3 ГБ volume, обмежений трафік — достатньо для довідкового сайту |
| Сон / холодний старт | Можна налаштувати автозупинку — перший запит після паузи трохи повільніший |
| Власний домен | Так, безкоштовно (свій домен або `*.fly.dev`) |

### Render

| | |
|---|---|
| Персистентність диска | Ні на free-плані — диск ефемерний, `quetzal_zsu.db` зникне при кожному передеплої/сні |
| Що потрібно | GitHub-репозиторій, акаунт Render — деплой без Docker (buildpack) |
| Ліміти free tier | 750 год/міс, 512 МБ RAM |
| Сон / холодний старт | Засинає після 15 хв без запитів, перше відкриття — 30–60 сек |
| Власний домен | Так, безкоштовно |

> **Обмеження:** підходить лише якщо база оновлюється рідко і ви готові вручну заливати оновлений `quetzal_zsu.db` при кожному деплої (наприклад, зберігаючи його в самому репозиторії).

### PythonAnywhere

| | |
|---|---|
| Персистентність диска | Так — файлова система постійна навіть на free-плані |
| Що потрібно | Акаунт, завантаження коду через їхній файловий менеджер або git; налаштування WSGI/ASGI вручну |
| Ліміти free tier | Обмежений CPU-час на день, 512 МБ дискового простору |
| Сон / холодний старт | Не засинає, але домен виду `username.pythonanywhere.com` |
| Власний домен | Ні на free-плані (потрібен платний план) |

### Підсумок

Для цього проєкту важливо, щоб `quetzal_zsu.db` зберігався між перезапусками — тому **Fly.io** єдиний з трьох, що дає і персистентний диск, і власний домен безкоштовно. PythonAnywhere — запасний варіант, якщо не хочеться працювати з Docker/CLI.
